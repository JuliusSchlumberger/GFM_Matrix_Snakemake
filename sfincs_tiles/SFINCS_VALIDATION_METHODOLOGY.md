# SFINCS validation of the eikonal flood model

## Purpose and motivation

The Global Flood Model (GFM) production pipeline estimates coastal inundation using an eikonal-equation solver: a cost-based attenuation model that propagates storm-tide water levels inland from the coast, trading physical completeness for the ability to run at global scale. To assess how well this approximation reproduces genuine hydrodynamics, we validated it against SFINCS, a reduced-physics but genuinely hydrodynamic (shallow-water) model, on a representative sample of tiles drawn from the production tile grid. The exercise also served a second purpose: because building and running real SFINCS models forced every stage of the shared DEM/mask/friction/boundary preprocessing to be exercised and cross-checked against an independent solver, it surfaced several real defects in the production preprocessing pipeline itself - most significantly a mask-classification bug that was silently truncating the flood boundary on some coastal tiles. These fixes have since been folded back into the production pipeline.

## Tile selection

Two non-overlapping sets of tiles, roughly 260 each, were drawn from the production tile grid (`domain_tiles_global.gpkg`), restricted to `hop_distance == 0` tiles - those with a genuine ocean edge of their own, rather than hinterland tiles seeded from an already-simulated neighbour. Both sets reused the eligibility checks already established for the production model's own test-tile selection (existing `mask.tif` within a maximum cell-count budget, no more than 1% river fraction, at least one real COAST-HG hydrograph station within a reasonable search radius of the tile), so the sample stayed representative of tiles the production pipeline can actually process end to end.

Set A was constructed to be a broad, globally representative sample: the smallest tiles by area, restricted to non-polar latitudes (|latitude| between 5° and 55°, to avoid the geometric degeneracies of extreme polar tiles), then spatially stratified across a coarse global grid so the sample wasn't clustered in any one region. Set B was constructed specifically to stress-test SFINCS's boundary-placement behaviour. SFINCS's own `create_boundary()` routine places water-level forcing only on ocean cells that lie on the active domain's own rectangular outer edge - not on the true coastline in general - so a cheap proxy for boundary quality was computed directly from each candidate tile's own `mask.tif`: the median distance from the tile's raster bounding-box edge to the nearest real land cell, via a Euclidean distance transform. Tiles with a small ocean fraction (5-50%, chosen after an initial 10-20% band proved to contain too few eligible tiles) and a small value of this boundary-distance proxy were preferentially selected, since these are the tiles where a poorly-placed or too-short a boundary segment would matter most, then spatially stratified in the same way as Set A to avoid regional clustering.

One additional geometric check was added during this exercise: any tile whose geometry spans an implausibly wide longitude range (a tell-tale sign of a polygon that wraps the antimeridian at ±180°) is excluded from both sets. This was added after discovering that `hydromt_sfincs`'s own internal geometry masking performs a raw EPSG:4326 union operation that produces a self-intersecting, GEOS-invalid polygon for any tile straddling the dateline - a failure mode with no fix available from this side (it lives inside `hydromt_sfincs`'s own dateline handling), so such tiles are simply dropped from the validation sample rather than chased further.

## Pipeline architecture

Each selected tile is processed by a fixed sequence of per-tile scripts, run under two different, mutually incompatible conda environments: an older-`hydromt`-pinned environment (`gfm`) required by the shared production code in `src/rasters.py` and `src/flood_model.py`, and a newer-`hydromt`-pinned environment (`hydromt-sfincs-dev`) required to build and run actual SFINCS models. The per-tile driver script switches between these environments by invoking each stage's interpreter directly by its full binary path rather than via `conda activate`, after discovering that shell-based environment activation is unreliable inside a non-interactive nested `bash` invocation (it silently falls back to the base environment instead of raising an error, producing a confusing `ModuleNotFoundError` deep inside an unrelated import rather than an obvious activation failure).

Every stage of the per-tile pipeline is idempotent, gated on the existence of its own expected output file, so that a batch can be re-run after a partial failure - or resubmitted entirely - without redoing work that already completed successfully. The full ~520-tile batch (Set A + Set B) is dispatched as a fixed number of independent Slurm batch scripts, each looping sequentially through its own slice of tiles and performing the complete per-tile sequence (input preparation, SFINCS model build, bathtub/eikonal solve, SFINCS run, postprocessing) before moving to the next tile in its slice; the batch scripts carry no dependency between them; each is scheduled onto a node as one becomes free, giving embarrassingly-parallel throughput across the whole tile set.

## Building each tile's SFINCS model

### Starting inputs

Each tile's DEM, DEM-validity mask, friction (Manning's n) raster, tile geometry, model bounding box, and pre-selected COAST-RP boundary-forcing points are first copied from the tile's own already-built production preprocessing output, giving the validation exercise a real, representative starting point rather than a synthetic test case.

### DEM and mask regeneration

Because the shared preprocessing code in `src/rasters.py` continued to be actively fixed throughout this exercise (see Findings below), each tile's `dem.tif` and `mask.tif` are then regenerated by calling the exact same `extract_dem`/`extract_dem_mask` functions the production Snakemake pipeline uses, rather than trusting whatever copy exists in the production output tree, which may predate a since-fixed bug. This keeps every validated tile on the current state of the shared DEM-extraction logic, and means every fix made to that shared code during the exercise applies automatically to both the validation batch and the production pipeline with no separate code path to keep in sync.

### Elevation surface

SFINCS additionally needs a genuine bathymetric elevation surface offshore, which the eikonal model's own DEM does not provide (it simply zero-fills every non-land cell). A combined elevation surface is built by taking DeltaDTM's own land elevation on land cells, and GEBCO's global bathymetry - corrected for the local mean dynamic topography (MDT) offset so it shares DeltaDTM's own vertical reference frame - on ocean cells, at the tile's native EPSG:4326 grid. This combined surface is deliberately kept completely separate from the eikonal model's own `dem.tif`, which is never touched by anything described in this section. The blended ocean elevation is clipped to a shallow envelope (roughly -10 m to 0 m): the deep floor exists because the storm-tide signal these tiles are forced with never reaches genuinely deep water, so far offshore bathymetry adds nothing but an unnecessarily wide elevation range for the solver; the shallow ceiling exists because GEBCO's own coarse native resolution was found to produce implausible above-sea-level spikes at some ocean-coded cells right at the DeltaDTM/GEBCO transition, which is definitionally impossible for open water and was confirmed to let flood water through a lagoon SFINCS's real solver treated as a barrier.

Lake and river cells receive special handling for a related reason: DeltaDTM has no genuine elevation measurement over open water, so the production DEM-extraction logic simply fills these cells to a flat 0 m regardless of gap size. A flat, artificially high lakebed or riverbed is trivially easy to flood from a shallow forcing signal with no real depth or channel resistance to overcome. For the SFINCS elevation surface specifically, lake and river elevation is instead re-derived from nearby valid land elevation via nearest-neighbour interpolation, then passed through a local spatial minimum filter along the water body so a single high bank pixel cannot locally "bridge" across a channel and block flood propagation, giving a much more physically plausible, connected low-lying channel profile than the flat fill.

A further, non-obvious fix was needed for land elevation specifically: `hydromt_sfincs`'s own subgrid volume-table builder applies a hardcoded floor of -20 m to any subgrid pixel elevation when computing each coarse cell's own water-level/volume lookup table, a value that is not exposed as a configurable parameter. This clamp is invisible in the true (unclamped) elevation used elsewhere in this pipeline's own postprocessing, so any land cell genuinely below roughly -18 m produces a large, entirely spurious "flood" from the mismatch between the model's clamped internal dry-state reference and the true elevation used to compute reported depth, with no real inflow or connectivity involved at all. This was traced to a specific below-sea-level basin (Lake Enriquillo, Dominican Republic) whose surrounding land is still recorded as dry in both DeltaDTM and the water-body mask, predating the lake's well-documented post-2004 expansion. All land cells are therefore floored 5 m above `hydromt_sfincs`'s own internal clamp as a margin, since this floor is applied at the coarser DEM pixel resolution while the actual clamp operates on the finer subgrid.

### Roughness

The eikonal model's own friction raster stores a solver-specific "slowness" convention (Manning's n divided by 100, further scaled for int16 storage) rather than a physically real Manning's n. This is decoded and rescaled back into a genuine Manning's n GeoTIFF (checked against a generous physical plausibility envelope, to catch a unit-conversion regression rather than unusual real land cover) before being handed to SFINCS's own roughness assignment.

### Boundary forcing

Each tile's pre-selected COAST-RP boundary points already carry a storm-tide water level for the target return period, empirically corrected for local MDT, but only as a single peak value - not a full time-varying hydrograph, which SFINCS's transient solver needs. To reconstruct a physically consistent hydrograph, each boundary point is matched to its nearest COAST-HG station (a companion dataset providing full storm hydrograph shapes without the MDT correction), and the empirical offset between the boundary point's own corrected peak value and the matched hydrograph's own raw peak is computed and added to the entire hydrograph series, recovering the same MDT correction across the whole time series rather than just at the peak. Only the k nearest of the eikonal model's own already-selected boundary points are used for SFINCS forcing (by default 20): the eikonal model's own boundary selection uses a roughly 100 km search radius appropriate for its own cost-distance seeding, but real measured distances showed some matched stations well over 100 km from the tile itself, and storm-tide phase and amplitude decorrelate well before that distance - blending such distant stations by inverse-distance weighting into a small local SFINCS domain is not physically appropriate the way it is for the eikonal model's own very different use of that same search radius.

### Model assembly

The SFINCS model itself is built on a coarse computational grid (120 m) with a four-times-finer subgrid table (30 m) capturing sub-cell terrain detail without the per-timestep cost of running the full simulation at that finer resolution - subgrid construction is a one-time preprocessing cost only. This 120 m/30 m combination followed a real A/B comparison against 90 m/15 m: at 15 m the subgrid table's forced nearest-neighbour-free (bilinear) interpolation, finer than DeltaDTM's own native ~30 m resolution, was found to fabricate small spurious depressions with no real source-data support, producing several metres of artefactual "flooding" that vanished once the subgrid resolution was coarsened back to DeltaDTM's own native scale. Elevation and roughness are pre-reprojected with nearest-neighbour resampling onto the exact destination subgrid before being handed to `hydromt_sfincs`, since it was found to silently force bilinear resampling internally regardless of the resampling method requested - the pre-reprojection guarantees every subgrid pixel is traceable to a real DeltaDTM or GEBCO sample rather than a blended value, and also keeps the SFINCS and eikonal models' own DEM values as close as possible for a fair comparison.

The active model domain covers the whole tile; water-level boundary cells are placed automatically by `hydromt_sfincs` on whichever ocean-coded cells of that domain's own rectangular outer edge fall inside a supplied ocean polygon (vectorised directly from the tile's own `mask.tif`). The forcing hydrograph is truncated from its full ~149-hour span down to a 70-hour window bracketing the storm peak, a real, confirmed roughly 2x wall-clock speedup with no discernible degradation in the reported maximum flood extent, since every tile's hydrograph in this dataset was confirmed to share the same synthetic time axis and peak timing rather than requiring individual per-tile tuning. The buffer radius `hydromt_sfincs` uses to decide which boundary points to include is computed dynamically from the real distance between the tile's own matched stations and the model grid, rather than a fixed guess, after a fixed buffer was found to occasionally exclude a tile's only available station and crash model construction outright with no partial-forcing fallback.

Initial water levels (`zsini`) are interpolated from the matched boundary stations' own first-timestep value via inverse-distance weighting, but - after discovering that applying this interpolated value across every grid cell, land included, was starting some tiles' simulations already "flooded" purely from the interpolated coastal water level being compared against real, very low inland terrain, with genuinely zero cells ever newly flooded by the simulated storm itself - this is now restricted to genuine ocean cells only, with every other cell explicitly left dry via `hydromt_sfincs`'s own bed-level-fallback sentinel.

## Running and comparing the three models

For every tile, three models are run and compared on exactly the same fine-resolution UTM subgrid: a naive "bathtub" fill (maximum boundary water level minus terrain elevation, with no attenuation or connectivity at all, serving as an upper-bound reference), the production eikonal solver run directly on SFINCS's own subgrid DEM and roughness inputs (rather than the eikonal model's own separately-built lon/lat grid), and SFINCS's own real hydrodynamic solve. Running the eikonal solver on SFINCS's own subgrid, rather than comparing across two independently-built grids, was a deliberate methodological choice: it isolates genuine differences in the two models' physics and numerics from every difference in grid, projection, or elevation source that would otherwise contaminate the comparison, since SFINCS's subgrid is a true, isotropic UTM metre grid, matches the eikonal model's own attenuation-rate calibration resolution, and already benefits from the exact same "flatten every non-land cell to a common reference" treatment the eikonal model normally applies to its own DEM.

Agreement between SFINCS and each of the other two models is quantified per tile as three raw area counts on that shared subgrid, above a uniform 0.05 m wet-cell threshold applied identically to all three depth rasters: cells where the model and SFINCS agree the cell is flooded ("matched"), cells where only the model under test claims flooding, and cells where only SFINCS claims flooding. No per-tile hit-rate/false-alarm/critical-success-index ratio is computed or stored - computing such a ratio from one tile's own small, noisy counts and then averaging it across tiles would let a small, lightly-flooded tile dominate the average exactly as much as a large, heavily-flooded one, which is not the statistically appropriate way to combine contingency-table metrics across regions of very different size. Instead, these three raw counts are computed once per tile, during the same postprocessing step that already has the relevant rasters open in memory on the compute node that just finished that tile's simulation, and written into that tile's own results summary; a separate, lightweight aggregation step then simply sums these counts across the whole batch and computes hit rate, false-alarm rate, critical success index, and bias exactly once, from the batch-wide totals.

## Findings

### Fixed during this exercise

Several genuine defects in the shared preprocessing pipeline were discovered and corrected as a direct result of cross-checking against SFINCS's independent hydrodynamics, and have been folded back into the production `extract_dem`/`extract_dem_mask` code path used by both the eikonal and SFINCS pipelines:

A source raster mosaic was found to carry two distinct representations of missing data - a literal sentinel value inherited from individual source tiles, and genuine `NaN` wherever the mosaic itself has no underlying source coverage at all - and only the literal sentinel was being recognised by the downstream gap-filling and encoding logic, letting a real coverage gap silently pass through as an incorrect, invisible sea-level (0 m) reading rather than being flagged and gap-filled like any other missing cell.

The most significant finding was a systematic mask-classification issue affecting elongated, coast-parallel tiles whose bounding box extends some distance offshore, beyond the real coverage of the DeltaDTM validity mask. Every cell in the resulting coverage gap was, by the existing conservative convention, classified as land - which is the correct, safe default for a genuinely data-sparse inland gap, but wrong for a gap that is simply far out at sea. Because SFINCS places its water-level boundary only on ocean cells that reach the active domain's own outer rectangular edge, a false "land" strip running along most of a tile's true coastline starved the boundary of almost its entire real coastal length, collapsing it to a tiny fraction of the tile's true coast and causing SFINCS to catastrophically under-flood the tile under real storm forcing. This was fixed by consulting GEBCO bathymetry wherever the DeltaDTM mask has no coverage: a coverage-gap cell is only reclassified from land to ocean if GEBCO independently reads negative there and the cell is connected, through a chain of other such cells, to at least one already-confirmed real ocean cell within the same tile - a safeguard specifically designed to protect genuinely isolated below-sea-level inland basins (two such cases, a below-sea-level lake and a below-sea-level rift basin, had already been documented elsewhere in this codebase) from being misclassified as ocean by a naive sign-only rule. On the tile used to diagnose this issue, the fix increased SFINCS's boundary-cell coverage from a single row (roughly 330 cells) to over 1,300 cells spanning 85% of the model grid's height, and brought SFINCS's reported flooded-cell count from roughly 7,000 - more than fifty times lower than either of the other two models - up to within the same order of magnitude as the eikonal and bathtub results for that tile.

Two further real bugs were specific to how initial and boundary conditions were being applied rather than the DEM/mask themselves: initial water levels were, for a period, being applied across every grid cell rather than ocean cells only, which was found to start some low-lying tiles' simulations already "flooded" from the interpolated coastal water level alone, with the entire final reported flood extent on the affected tiles turning out to be cells that were already wet before the simulated storm ever began; and the boundary-inclusion buffer radius `hydromt_sfincs` uses when selecting which forcing stations to include was, for a period, a fixed guess rather than computed from the real distance between a tile's own matched stations and its model grid, which was found to occasionally exclude a tile's only available forcing station entirely and crash model construction.

### Understood, not yet addressed

Two further sources of disagreement between the eikonal and SFINCS models were investigated and are understood, but represent either an inherent limitation of the eikonal formulation or an open calibration question rather than a bug with an available fix. On one tile with a genuinely amplifying local shoreline geometry, SFINCS's real hydrodynamics produced local water-level amplification exceeding the maximum boundary forcing itself, something the eikonal model's pure attenuation-from-boundary formulation cannot represent by construction, since it has no mechanism to model water piling up locally beyond its source value. On a separate tile with a wide, flat, low-gradient coastal plain, the eikonal model's calibrated friction-based attenuation rate - calibrated against a small number of real validation tiles - was found to over-attenuate relative to SFINCS's own, much shallower measured water-level gradient for that specific kind of terrain, suggesting the current calibration may not generalise well to wide flat coastal plains specifically. Neither of these has a code fix implemented; both are flagged here as open findings from the validation exercise for future calibration or methodology work.

## Results

Across the batch of tiles successfully run through the full pipeline, pooling raw agreement counts across every tile rather than averaging per-tile ratios, SFINCS was compared against both simpler models:

| Metric | SFINCS vs. bathtub | SFINCS vs. eikonal |
|---|---|---|
| Hit rate | 0.99 | 0.66 |
| False-alarm rate | 0.68 | 0.12 |
| Critical success index | 0.32 | 0.61 |
| Bias | 3.06 | 0.74 |

The bathtub reference, as expected, captures almost every cell SFINCS floods (hit rate near 1) but at the cost of massively over-predicting total flooded area (bias above 3, roughly two-thirds of its own flooded area being a false alarm relative to SFINCS), consistent with its complete lack of attenuation or connectivity. The eikonal model shows substantially better overall skill (critical success index roughly double the bathtub reference's) with a low false-alarm rate - most of what it predicts as flooded is confirmed by SFINCS - at the cost of being somewhat conservative, missing on the order of a third of SFINCS's own flooded area in aggregate (bias below 1), consistent with the deliberately conservative, attenuation-only nature of its formulation.

## Known follow-up work

The two-set tile selection described above (Set A + Set B) has a known asymmetry: only Set A was restricted to non-polar latitudes (|lat| 5-55°); Set B carried no latitude restriction at all, so 56% of Set B (127 of 260 tiles, 96 of those above the Arctic/Antarctic Circle) ended up outside that band - not a deliberate design choice, just an inconsistency between the two sets' own criteria, visible directly on the tile-locations map. The plan is to redo tile selection as a single ~520-tile pass with no A/B split and, per further user direction, no latitude restriction at all (take from the full range, poles included, rather than re-applying Set A's band inconsistently) - smallest-by-area, antimeridian-excluded, spatially stratified, with a new floor of ocean fraction >= 5% applied to every selected tile. The same script should also generate a global Equal Earth tile-locations map (light grey land, no figure title), a histogram of the selected sample's size/ocean-fraction distribution against the eligible pool, and an Excel workbook with the summary statistics tables - then the whole validation batch needs to be re-run against that corrected sample. This is currently blocked: the selection logic reads each candidate tile's `mask.tif`/`boundaries_RP100_SLR_0.gpkg` from `model_outputs/{tile_id}/inputs/`, and `model_outputs/` was deliberately deleted (2026-09-24) to force a clean rebuild of the production preprocessing pipeline after the GEBCO-based mask fix. Re-run tile selection once `model_outputs/` exists again.
